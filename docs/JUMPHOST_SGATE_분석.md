# 오프라인 점프호스트(S-gate) 경유 운영의 기술적 제약 분석

| 문서 정보 | 내용 |
| --- | --- |
| 제목 | 오프라인 점프호스트(S-gate) 경유 운영의 기술적 제약 분석 |
| 대상 시스템 | HPC 클러스터 자동화 시스템 (Apptainer 기반 전·후처리 배포) |
| 분석 범위 | Windows 점프호스트(S-gate) 경유 시 빌드 자동화·전노드 동기화의 기술적 활용 난이도 |
| 작성 근거 | 시스템 실제 배포·동기화 코드 (`sync_apptainers_to_nodes.sh`, `phase10_compute_deploy.sh`) |

---

## 핵심 요약 (Executive Summary)

- **본 시스템의 가치 모델**은 "사내 리눅스 빌드 서버의 자동 빌드 → 관리 서버가 전 노드
  (346대)에 **직접·병렬·무인·증분** rsync로 즉시 동기화"하는 **빌드-배포 무인 연쇄**다.
- **Windows 점프호스트(S-gate)** 는 설계상 ① 임의 터널·포워딩 차단, ② 대화형 인증 강제,
  ③ 세션 직렬화·동시연결 제한, ④ POSIX 메타데이터 비보존을 본질로 하며, 위 네 전제
  (직접·병렬·무인·증분)와 빌드 산출물 전달 단계를 **동시에 무력화**한다.
- **결과**: 점프호스트 경유는 단순한 속도 저하가 아니라 **자동화 모델 자체가 성립하지
  않는 구조적 제약**이다. 특히 346대 규모에서는 게이트 단일 통과 병목이 비선형으로
  악화되어 3일~1주일 동기화 주기를 충족할 수 없다.
- **대체 방안(6종) 검토 결과**, 모두 (a) 보안정책 예외 승인, (b) 폐쇄망 신규 자산 도입
  절차, (c) 무인 자동화와 대화형 게이트의 원리적 충돌 중 하나 이상에 막혀 **운영 목표를
  충족하지 못한다.** 가장 현실적인 절충(게이트 안쪽 중계 미러)조차 1차 반입이 게이트를
  통과하는 한 완전 자동화는 달성되지 않는다.
- **장기 비전과의 단절**: S-gate는 한 시스템의 배포를 넘어, **사내 GitHub → 개발 서버
  빌드(CI) → HPC 서비스 배포(CD)** 로 이어지는 그룹 통합 CI/CD 자동화 비전 자체를
  차단한다. 코드 커밋 한 번으로 전 노드까지 반영되는 GitOps형 흐름이, 게이트 구간에서
  **사람의 수동 개입 단계로 퇴화**한다.

## 1. 분석 전제

### 1.1 운영 형태 (요구사항)

| 항목 | 내용 |
| --- | --- |
| 배포 단위 | Apptainer `.sif` 컨테이너 (전·후처리 프로그램 모두 내장) |
| 빌드 방식 | 사내 리눅스 빌드 서버에서 정의/소스 변경 시 자동 빌드 → 산출물(`.sif`) 자동 동기화 |
| 업데이트 주기 | 3일 ~ 1주일 (고빈도) |
| 배포 범위 | 전체 노드 일괄 — controllers 3 + compute 약 343 = **총 346대** |
| 1회 전송량 | 노드당 약 8.7 GB (예: `vnc_gnome_lsprepost` 1.3 GB, `sunshine` 1.4 GB 등 다수) |
| 전노드 합계 | 약 8.7 GB × 346 ≈ **3.0 TB** (전량 기준), 증분 동기화 시 변경분만 전송 |
| 동기화 방식 | rsync 증분 동기화 (`-avz --ignore-existing` / `--progress`) + tar 압축 + 병렬(3~10) SSH |
| 운영 목표 | 빌드 서버 산출물을 전 노드에 **항상 최신으로 자동 동기화** 유지 |

### 1.2 핵심 메커니즘 (코드 근거)

| 구성요소 | 동작 |
| --- | --- |
| `sync_apptainers_to_nodes.sh` | 샌드박스를 `tar czf` 압축 → `rsync -avz` 전송 → 원격 전개. SSH 키 기반(`-i`) + sshpass 폴백 |
| `phase10_compute_deploy.sh` | `--parallel N`(기본 3, 대규모 자동 5~10)으로 다수 노드 동시 SSH/scp 배포, `apt_packages` 존재 시 스킵(증분) |
| 공통 SSH 패턴 | `ssh -o BatchMode=yes -o ConnectTimeout=… <user>@<ip>`, 실패 시 `sshpass -e`(키→비번 폴백), 표준 포트 22 |

> **전제**: 모든 자동화는 "관리 서버 ↔ 각 노드"의 **직접·양방향·다중 SSH/rsync 세션**을
> 기반으로 한다. 점프호스트(S-gate)가 이 경로 중간에 위치하면 이 전제가 깨진다.

## 2. 점프호스트(S-gate) 경유가 기술적으로 어려운 이유

### 2.1 rsync 증분 동기화의 양방향 채널 전제 붕괴

rsync의 효율(증분·`--ignore-existing`·델타 전송)은 로컬과 원격이 **한 SSH 세션 위에서
파일 목록·체크섬을 양방향 교환**하는 데서 비롯된다. 본 시스템은
`rsync -avz … <user>@<node>:<dir>` 형태로 관리 서버가 각 노드에 직접 세션을 연다.

- **투명 포워딩 미보장**: Windows 점프호스트는 OpenSSH `ProxyJump`/`ProxyCommand`의
  투명한 TCP 포워딩을 보장하지 못한다. S-gate류 게이트웨이는 대개 (a) 대화형 터미널만
  중계하고 `-J`/`-W`/포트포워딩을 차단하거나, (b) 세션을 프로토콜 레벨에서 가로채(SSH
  proxy) rsync가 기대하는 raw 채널을 변형한다. 그 결과 원격 셸 호출(`rsync --server`)이
  게이트의 셸/래퍼에 막혀 **델타 전송 실패 또는 전량 재전송으로 퇴화**한다.
- **세션 상태(stateful) 붕괴**: 게이트가 감사·격리를 위해 세션을 끊거나 재인증을
  요구하면, rsync의 "목록 협상 → 전송 → 검증" 연속 수행이 중단되어 **부분 전송·체크섬
  불일치**가 발생한다.

### 2.2 병렬 다중 세션 모델과 게이트 직렬화의 충돌

`phase10_compute_deploy.sh`는 다수 노드에 병렬(3~10) SSH/scp를 동시에 연다. S-gate는
본질적으로 **세션을 한 곳에 모아 검사·기록·직렬화**하는 장치다.

- **동시 세션 제한·큐잉**: 게이트가 동시 연결 수를 제한하면 병렬 배포가 직렬화되어,
  전체 전송이 사실상 순차 처리된다. 고빈도 주기에서 동기화 윈도우 내 완료가 불가능해진다.
- **단일 병목·대역폭 집중**: 모든 트래픽이 게이트 1대를 통과하므로 **게이트의
  NIC/디스크/CPU가 병목**이 된다. tar+rsync 압축에도 노드당 8.7 GB가 한 점에 수렴한다.

### 2.3 무인(비대화형) 자동화와 대화형 보안 게이트의 충돌

본 시스템의 배포는 cron/스크립트 기반 **무인 실행**(`BatchMode=yes`, 키 인증, sshpass
폴백)을 전제로 한다. S-gate(특히 Windows 보안 게이트)는 정반대 가정 위에 설계된다.

- **대화형 인증 강제**: OTP·SSO·캡차·매 세션 승인·녹화 동의 등 사람의 개입을 요구하면
  `BatchMode`/키 기반 무인 rsync가 **원천적으로 통과 불가**하다.
- **공개키 인증 차단/변형**: 게이트가 비밀번호·OTP만 허용하고 공개키를 막으면, 키→sshpass
  폴백 체계가 **키는 막히고 비번도 OTP라 자동 입력 불가** 상태가 된다.
- **세션 TTL/유휴 종료**: 대형 `.sif` 전송(수 분~수십 분) 중 게이트 유휴 타임아웃이
  걸리면 전송이 끊긴다.

### 2.4 프로토콜·포트·경로 측면의 비호환

- **포트포워딩/터널 차단**: 본 시스템은 SSH 터널(예: VNC noVNC 프록시 `create_ssh_tunnel`),
  scp/rsync 채널을 적극 사용한다. 게이트가 포워딩을 막으면 **서비스 기능 자체(원격 데스크탑
  프록시 등)까지 동작 불가**하다.
- **Windows–POSIX 메타데이터 비보존**: 점프호스트가 Windows이면 그 위에서 rsync/ssh
  래퍼를 거칠 때 **POSIX 권한(1777/0644)·심볼릭 링크·`sudo`·소유자 의미가 보존되지
  않는다.** 본 시스템은 권한·UID/GID 동기화에 의존하므로(예: VNC 디렉토리 1777, 노드 간
  UID 일치), 경유 중 메타데이터가 유실되면 **배포는 되었으나 실행 권한이 깨지는** 문제가
  발생한다.
- **2-hop 우회의 취약성**: 게이트를 "복사 → 재복사"의 2단계로 우회하면 각 hop마다
  디스크 IO·임시 저장·정합성 검증이 중복되어 **증분성·원자성이 사라진다.**

### 2.5 규모(346대)에 따른 병목의 비선형 악화

배포 대상이 346대라는 점은 위 제약을 산술이 아니라 **비선형으로** 키운다.

- **단일 게이트 통과 × 346**: 노드별 직접 전송이면 내부 스위치 대역폭을 346갈래로
  나눠 쓰지만, 게이트 경유는 모든 흐름이 게이트 1대의 NIC·세션 테이블·감사 로깅을
  통과한다. 게이트의 동시 세션·throughput 상한이 전체 동기화 시간을 지배한다.
- **부분 실패 확률 증가**: 346대 × (수 분~수십 분) 전송에서 게이트의 세션 TTL·재인증·큐
  드롭이 발생할 확률이 노드 수에 비례해 커진다. 한 노드라도 부분 전송/체크섬 불일치면
  "전 노드 최신" 불변식이 깨진다.
- **재시도 폭증**: 실패 노드 재시도가 다시 게이트를 통과하며 피크 부하가 눈덩이처럼
  커져, 동기화 윈도우 초과가 상시화된다.

### 2.6 빌드 파이프라인(사내 리눅스 빌드 서버)의 게이트 종속

본 시스템은 단순 배포가 아니라 **빌드 → 동기화가 연결된 무인 파이프라인**이다.
apptainer 정의/소스 변경 시 사내 리눅스 빌드 서버가 자동으로 `.sif`를 빌드하고 산출물을
클러스터로 자동 동기화한다. 빌드 서버와 클러스터(또는 관리 서버) 사이에 S-gate가 놓이면
**빌드 자동화의 산출물 전달 단계가 통째로 게이트에 묶인다.**

- **무인 연쇄 단절**: 빌드는 자동으로 끝나도, 결과를 게이트 너머로 보내는 마지막 hop이
  대화형 인증·세션 승인을 요구하면 파이프라인이 사람의 개입 지점에서 정지한다. 빌드가
  잦을수록 수동 개입 빈도가 운영 부담으로 누적된다.
- **2단(빌드서버 → 게이트 → 클러스터) 경유**: 산출물은 (a) 빌드 서버 → 관리 서버/미러
  1차 전달, (b) 거기서 346대로 2차 배포의 2단계를 거치며, 게이트가 1차 단계에 끼면
  2.1~2.4의 모든 제약이 산출물 전달에 그대로 재현된다.
- **빌드-배포 원자성 상실**: 이상적으로는 "빌드 버전 N이 전 노드에 일괄 반영"되어야
  버전 정합성이 보장된다. 게이트가 일부만 통과시키면 **노드 간 버전 혼재**(일부 N, 일부
  N-1)가 발생해, 동일 잡이 노드에 따라 다른 전·후처리 바이너리로 도는 **재현성·정합성
  사고**로 이어진다.
- **CI/CD 단절**: 빌드 서버의 자동 빌드는 사실상 CI다. CI 산출물을 무인으로 배포처에
  push하지 못하면 CD가 성립하지 않으며, **게이트가 그 CD 경로의 단절점**이 된다.

### 2.7 소결

본 시스템의 자동화 가치는 "사내 빌드 서버 자동 빌드 → 관리 서버가 346대에 직접·병렬·
무인·증분 rsync 즉시 동기화"하는 **빌드-배포 무인 연쇄**에 있다. S-gate는 그 네 전제와
빌드 → 배포 자동 전달 단계를 동시에 약화시키므로, 점프호스트 경유는 **단순한 속도 저하가
아니라 빌드 자동화·일괄 배포 모델 자체가 성립하지 않는 구조적 제약**이다.

## 3. 대체 방안 검토

| # | 대체 방안 | 개요 | 핵심 한계 |
| --- | --- | --- | --- |
| A | OpenSSH ProxyJump(`-J`)/ProxyCommand 터널링 | S-gate를 SSH 다중-hop으로 투명 경유, rsync를 그 위로 | 게이트의 터널·포워딩 차단 시 불성립 |
| B | 게이트 안쪽 중계 미러(스테이징) 서버 | 외부 → 미러 1회, 미러 → 전노드 병렬 | 신규 호스트 도입 승인 + 1차 반입이 게이트 통과 |
| C | 풀(pull) 모델 + 내부 콘텐츠 미러 | 각 노드가 정시에 내부 미러에서 스스로 pull | 미러 최신화가 게이트 의존 (B 제약 상속) |
| D | 오프라인 매체(스니커넷) 정기 반입 | `.sif`/패키지를 물리 매체로 주기 반입 | 무인 자동화 원칙 위배 + 매 회 검역 행정 |
| E | 델타/블록 동기화 도구 전환(zsync·casync·torrent) | 게이트 통과 데이터량 축소 | 채널 자체를 못 여는 문제는 동일 + 신규 포트 불가 |
| F | 컨테이너 레지스트리(OCI) 기반 배포 | `.sif` 대신 OCI 이미지를 내부 레지스트리 push/pull | 레지스트리 외부 갱신이 게이트 의존 + 신규 체계 구축 |

각 방안의 적용 어려운 사유는 4장에서 일대일로 서술한다.

## 4. 대체 방안별 적용이 어려운 사유

### 4.1 A안 — ProxyJump / ProxyCommand 터널링

- 게이트가 **SSH 포트포워딩·`-J`·`-W`를 정책적으로 차단**하면 ProxyJump 자체가 성립하지
  않는다(2.4). 보안 게이트의 존재 이유가 "임의 터널 차단"이므로, 허용은 **보안정책 예외
  승인** 문제로 귀결된다.
- 허용되더라도 **대화형 인증(OTP/SSO)** 이 끼면 무인 ProxyJump가 불가하다(2.3).
- 게이트가 **SSH 프록시(프로토콜 종단·재개시)** 형태면 raw 채널이 깨져 rsync 델타가
  무력화된다(2.1).

### 4.2 B안 — 게이트 안쪽 중계 미러(스테이징)

- 가장 현실적이나, **게이트 안쪽에 상시 가동 서버 1대를 신규 배치·운영**해야 한다.
  자산 도입·전력·관제·보안 인증(망분리 환경 신규 호스트 등록)에 대한 별도 승인·검증
  절차가 필요하며, 폐쇄망에서는 그 자체가 장기 행정 과제다.
- 외부 → 미러 1회 전송도 결국 **게이트를 통과**하므로, 게이트가 대화형·직렬화면 고빈도
  대용량 반입 윈도우를 보장하지 못한다(2.2).
- 미러 → 전노드는 내부망이라 빠르지만, **미러 최신성**을 보장하려면 외부 동기화가
  무인이어야 하는데 그 지점이 다시 게이트 제약에 묶인다(2.3).

### 4.3 C안 — 풀(pull) 모델 + 내부 콘텐츠 미러

- 각 노드가 스스로 당기려면 **내부 미러가 항상 최신**이어야 하고, 그 미러를 외부에서
  갱신하는 경로가 다시 게이트를 통과한다(4.2와 동일 병목).
- 노드 측 cron pull은 **노드의 외부 도달성**을 요구하나, 폐쇄망 정책상 compute 노드가
  게이트 너머를 직접 보는 것은 통상 금지된다. 결국 "미러까지만 push, 노드는 미러에서
  pull"로 귀착되어 **B안 제약을 그대로 상속**한다.

### 4.4 D안 — 오프라인 매체(스니커넷) 정기 반입

- 3일~1주일 주기로 **갱신분(GB 단위)을 사람이 물리 반입**해야 한다. "항상 최신 자동
  동기화"라는 목표 및 **무인 자동화 원칙에 정면으로 배치**된다(2.3).
- 매체 반입은 **보안 검역(악성코드 검사·반입 승인·매체 등록)** 을 매 회 거쳐야 하므로,
  짧은 주기에서는 **행정 비용이 전송 비용을 압도**한다.
- 증분성이 없어 매 회 전량·수동 관리 → 정합성·이력 추적이 취약하다.

### 4.5 E안 — 델타/블록 동기화 도구 전환(zsync·casync·torrent)

- 게이트 통과 데이터량은 줄일 수 있으나, **게이트가 raw TCP/포워딩을 막는 한**(2.1, 2.4)
  어떤 도구든 **채널 자체를 열지 못하는** 문제는 동일하다. "경유 가능성"이 해결되지
  않으면 도구 교체는 무의미하다.
- 폐쇄망·보안망에서 **신규 프로토콜/포트(torrent 등) 허용**은 보안정책상 거의 불가하다.
- 노드 측 신규 클라이언트(casync 등) 도입도 **오프라인 패키지 검증 체계**에 항목이
  추가되어 유지보수 부담이 증가한다.

### 4.6 F안 — 컨테이너 레지스트리(OCI) 기반 배포

- 본 시스템은 **단일 파일 `.sif`** 를 직접 rsync하는 모델이다. 레지스트리 전환은
  **빌드 파이프라인·노드 pull 체계·레지스트리 서버**를 새로 세워야 하며, 그 레지스트리도
  외부 갱신 시 **게이트를 통과**한다(4.2 병목 상속).
- 레지스트리 pull도 **노드의 레지스트리 도달성**을 요구 → 폐쇄망에서 내부 레지스트리로
  귀착되고, 그 최신화는 다시 게이트에 의존한다.
- OCI 레이어 캐시 이점은 있으나, 전·후처리 프로그램이 통째 든 대형 단일 이미지를 고빈도로
  통째 갱신하는 패턴에서는 **레이어 재사용 이득이 작다**.

## 5. 장기 비전(그룹 통합 CI/CD)과의 단절

본 시스템의 빌드-배포 자동화는 단독 시스템에 머무르지 않고, **그룹 전체의 통합 CI/CD
파이프라인으로 확장**되는 것을 지향한다. 목표 흐름은 다음과 같다.

```text
[사내 GitHub] → [개발 서버 빌드 자동화(CI)] → [HPC 서비스 배포 자동화(CD)] → [346대 운영]
   소스 push        apptainer 자동 빌드           전 노드 무인 동기화          서비스 반영
```

즉 그룹 내 자동화 프로그램을 **사내 GitHub에 올리면**, 개발 서버가 그 변경을 트리거로
**자동 빌드**하고, 그 산출물이 **HPC 서비스 자동화(전 노드 일괄 배포)까지 끊김 없이
이어지는** end-to-end 무인 연쇄를 구성하려는 것이다.

S-gate가 이 흐름의 **개발 서버 ↔ HPC 운영망 경계**에 놓이면, 이 통합 비전이 다음과
같이 무너진다.

- **GitHub → 빌드 → 배포의 자동 트리거 체인 단절.** GitHub push가 개발 서버 빌드까지는
  자동으로 이어져도(CI), 그 산출물을 HPC 운영망으로 넘기는 **마지막 CD 구간이 게이트의
  대화형 인증·터널 차단에 막힌다**(2.3, 2.4, 2.6). 결과적으로 "코드 커밋 한 번으로 전
  노드 반영"이라는 GitOps형 자동화가 **사람이 게이트에서 산출물을 손으로 넘기는 수동
  단계**로 퇴화한다.
- **파이프라인 가시성·추적성 상실.** 통합 CI/CD의 장점은 GitHub 커밋부터 노드 반영까지
  단일 파이프라인에서 **버전·이력·롤백이 추적**된다는 점이다. 게이트에서 끊기면 그 너머
  구간은 파이프라인 밖의 수동 작업이 되어, **어느 커밋이 어느 노드에 반영됐는지** 자동
  추적이 불가능해진다(2.6의 버전 혼재 위험과 직결).
- **확장성 단절.** 이 비전은 본 시스템뿐 아니라 **그룹 내 여러 자동화 프로그램**을 같은
  GitHub→빌드→HPC 경로에 태우는 것을 전제한다. 게이트가 모든 산출물 전달의 공통 경로가
  되면, 프로그램 수·빌드 빈도가 늘수록 **게이트 병목과 수동 개입이 곱으로 증가**한다.
- **DevOps 표준과의 불일치.** 사내 GitHub 기반 CI/CD는 무인·재현·자동 롤백을 표준으로
  한다. 대화형 보안 게이트는 그 표준의 전제(무인 자동 전달)와 원리적으로 충돌하므로,
  HPC 구간만 **표준 파이프라인에서 분리된 예외 영역**으로 남게 된다.

요컨대 S-gate는 "한 시스템의 배포"를 어렵게 하는 데 그치지 않고, **사내 GitHub 기반
그룹 통합 CI/CD가 HPC 서비스 자동화까지 이어지는 장기 비전 자체를 차단**한다.

## 6. 결론

본 시스템의 배포·동기화 자동화는 "사내 리눅스 빌드 서버의 자동 빌드 → 관리 서버가 346대
전 노드에 직접·병렬·무인·증분 rsync로 즉시 동기화"하는 **빌드-배포 무인 연쇄** 위에
서 있다(코드 근거: `sync_apptainers_to_nodes.sh`, `phase10_compute_deploy.sh`). 이
연쇄는 네 전제 — **직접·병렬·무인·증분** — 와 **빌드 → 배포 자동 전달**에 의존한다.

Windows 점프호스트(S-gate)는 설계상 **임의 터널·포워딩 차단, 대화형 인증 강제, 세션
직렬화·감사·동시연결 제한, POSIX 메타데이터 비보존**을 본질로 하므로, 위 네 전제와 빌드
산출물 전달 단계를 동시에 약화시킨다. 특히 **346대 규모**에서는 게이트 단일 통과 병목과
부분 실패 확률이 비선형으로 커져 3일~1주일 동기화 주기 내 완료가 사실상 불가능하다(2.5).
또한 빌드 서버가 게이트 너머에 있으면 **CI(자동 빌드)는 되어도 CD(무인 일괄 배포)가
단절**된다(2.6).

검토한 대체 방안(A~F)은 모두 "게이트를 통과하는 자동·무인·증분 경로"라는 근본 난점으로
수렴하며, 각 방안은 (a) 보안정책 예외 승인(터널·신규 포트 허용), (b) 폐쇄망 신규 자산
도입 절차(미러·레지스트리 호스트 등록·검증), (c) 무인 자동화와 대화형 게이트의 원리적
충돌 중 하나 이상에 막혀 **3일~1주일 주기의 346대 최신 동기화라는 운영 목표를 충족하지
못한다.**

따라서 점프호스트(S-gate) 경유 구조에서는 본 시스템이 제공하는 **빌드 자동화와 고빈도·
대용량·무인 일괄 동기화의 핵심 가치를 그대로 살리기 어렵다.** 이를 우회하려면 **게이트
안쪽 중계 미러(B안)에 대한 보안·행정 승인**과 **빌드 서버 ↔ 미러 간 무인 전달 경로
확보**를 동시에 전제로 한 부분적 절충만이 현실적 후보로 남는다. 그러나 그 절충마저
빌드 산출물의 1차 반입이 게이트를 통과해야 하는 한, **빌드-배포 무인 연쇄의 완전한
자동화는 달성되지 않는다.**

나아가 이 제약은 본 시스템 한 건에 국한되지 않는다. **사내 GitHub → 개발 서버 빌드
(CI) → HPC 서비스 배포(CD)** 로 이어지는 **그룹 통합 자동화 비전**(5장)에서, S-gate는
개발망과 HPC 운영망의 경계에서 CD 구간을 끊는 **구조적 단절점**이 된다. 결과적으로
그룹이 지향하는 "커밋에서 운영 반영까지 무인 연속" 파이프라인은 HPC 영역에서만
**표준 밖의 수동 예외 구간**으로 남게 되며, 이는 향후 자동화 프로그램 수와 빌드 빈도가
늘수록 운영 부담과 정합성 위험을 가중시킨다.
