# 오프라인 점프호스트(S-gate) 경유 운영의 기술적 제약 분석

## 0. 문서 목적과 전제

본 문서는 **본 HPC 클러스터 자동화 시스템**을, 또 하나의 오프라인 서버를
**점프호스트(Windows 기반 S-gate)** 뒤에 두고 운영·관리할 때의 기술적 활용
난이도를 분석한다. 분석은 추상론이 아니라 **본 시스템이 실제로 사용하는 배포·동기화
메커니즘**(`sync_apptainers_to_nodes.sh`, `phase10_compute_deploy.sh`,
rsync/scp/SSH 멀티노드)을 근거로 한다.

### 0.1 운영 형태(요구사항)

| 항목 | 내용 |
|------|------|
| 배포 단위 | Apptainer `.sif` 컨테이너 (전·후처리 프로그램까지 모두 내장) |
| 빌드 방식 | **사내 리눅스 빌드 서버**에서, apptainer 정의/소스에 변경이 있으면 **자동 빌드** → 빌드 산출물(`.sif`)을 클러스터로 **자동 동기화** |
| 업데이트 주기 | **3일 ~ 1주일** (매우 짧음) |
| 배포 범위 | **전체 노드 일괄** (controllers 3 + compute **약 343** = **총 346대**) |
| 1회 전송량 | 노드당 **약 8.7 GB** (vnc_gnome_lsprepost 1.3 GB, sunshine 1.4 GB 등 다수 `.sif`) → 전노드 합 **≈ 8.7 GB × 346 ≈ 3.0 TB**(전량 기준), 증분 시 변경분만 |
| 동기화 방식 | **rsync 증분 동기화**(`-avz --ignore-existing`/`--progress`) + tar 압축 + 병렬(3~10) SSH |
| 목표 | 빌드 서버에서 자동 빌드된 결과를 **전 노드에 항상 최신으로 자동 동기화** 유지 |

> 본 yaml 예시는 축소본(27대)이나, **실제 운영 규모는 controllers 3 + compute ≈ 343 = 총 346대**다.
> 규모가 커질수록 1.2(병렬/직렬화 병목)와 게이트 단일 통과 병목이 비선형적으로 악화된다.

### 0.2 핵심 메커니즘(코드 근거)

- `sync_apptainers_to_nodes.sh`: 샌드박스를 `tar czf`로 압축 → `rsync -avz` 전송 →
  원격에서 전개. SSH **키 기반**(`-i $key`) + sshpass 폴백.
- `phase10_compute_deploy.sh`: `--parallel N`(기본 3, 대규모 시 자동 5~10) 으로
  **여러 노드 동시 SSH/scp 배포**, `apt_packages` 존재 시 스킵(증분).
- 공통 SSH 패턴: `ssh -o BatchMode=yes -o ConnectTimeout=… <user>@<ip>`,
  실패 시 `sshpass -e`(키→비번 폴백). 표준 포트 22 + (Redis Sentinel 등) 부가 포트.

→ **이 모든 자동화는 "관리 서버 ↔ 각 노드"의 직접적·양방향·다중 SSH/rsync 세션을
전제**로 한다. 점프호스트(S-gate)가 이 경로 중간에 끼면, 그 전제가 깨진다.

## 1. 점프호스트(S-gate) 경유가 기술적으로 어려운 이유

### 1.1 rsync 증분 동기화의 양방향 채널 전제가 깨짐

rsync의 효율(증분·`--ignore-existing`·델타 전송)은 **로컬과 원격이 한 SSH 세션 위에서
파일 목록·체크섬을 양방향으로 교환**하는 데서 나온다. 본 시스템은
`rsync -avz … <user>@<node>:<dir>` 형태로 **관리 서버가 각 노드에 직접** 세션을 연다.

S-gate가 중간에 있으면 이 단일 양방향 채널이 다음 이유로 성립하기 어렵다.

- **Windows 점프호스트는 OpenSSH `ProxyJump`/`ProxyCommand`의 투명한 TCP 포워딩을
  보장하지 못한다.** S-gate류 보안 게이트웨이는 대개 (a) 대화형 터미널만 중계하고
  포트포워딩/`-J`/`-W`를 차단하거나, (b) 세션을 **프로토콜 레벨에서 가로채(SSH proxy)**
  rsync가 기대하는 raw 채널을 변형한다. 그 결과 rsync의 원격 셸 호출
  (`rsync --server …`)이 점프호스트의 셸/래퍼에 가로막혀 **델타 전송이 아니라 아예
  연결이 실패**하거나, 매번 전량 재전송으로 퇴화한다.
- **세션 상태(stateful) 전제 붕괴.** S-gate는 감사·격리를 위해 세션을 끊거나
  재인증을 요구하는 경우가 많은데, rsync는 한 세션 안에서 파일 목록 협상→전송→검증을
  연속 수행해야 한다. 중간 끊김은 **부분 전송·체크섬 불일치**로 이어진다.

### 1.2 병렬 다중 세션 모델과 게이트웨이 직렬화의 충돌

`phase10_compute_deploy.sh`는 27대에 **병렬(3~10) SSH/scp**를 동시에 연다.
S-gate는 본질적으로 **세션을 한 곳에 모아 검사·기록·직렬화**하는 장치다.

- **동시 세션 수 제한·큐잉.** 점프호스트가 동시 연결 수를 제한하면 병렬 배포가
  직렬화되어, 27대 × 8.7 GB ≈ **235 GB**를 사실상 순차 전송하게 된다. 3일~1주일
  주기로 이를 반복하면 동기화 윈도우 내 완료가 불가능해진다.
- **단일 병목·대역폭 집중.** 모든 트래픽이 S-gate 1대를 통과하므로, 노드별 직접
  전송 대비 **게이트웨이 NIC/디스크/CPU가 병목**이 된다. tar+rsync로 압축해도
  8.7 GB×27대가 한 점을 지난다.

### 1.3 비대화형(무인) 자동화와 대화형 보안 게이트의 충돌

본 시스템의 배포는 **cron/스크립트 기반 무인 실행**을 전제로 한다
(`BatchMode=yes`, 키 인증, sshpass 폴백). S-gate(특히 Windows 보안 게이트)는
정반대 가정 위에 설계된다.

- **대화형 인증 강제.** OTP·SSO·캡차·매 세션 승인·세션 녹화 동의 등 **사람의 개입**을
  요구하면, `BatchMode`/키 기반 무인 rsync가 **원천적으로 통과 불가**하다.
- **공개키 인증 차단/변형.** 게이트가 비밀번호·OTP만 허용하고 공개키를 막으면,
  본 시스템의 키→sshpass 폴백 체계가 **키는 막히고 비번도 OTP라 자동 입력 불가**한
  상태가 된다.
- **세션 TTL/유휴 종료.** 대형 sif 전송(수 분~수십 분) 도중 게이트의 유휴 타임아웃이
  걸리면 전송이 끊긴다.

### 1.4 프로토콜·포트·경로 측면의 비호환

- **포트포워딩/터널 차단.** 본 시스템은 SSH 터널(예: VNC noVNC 프록시,
  `create_ssh_tunnel`), scp/rsync 채널을 적극 사용한다. S-gate가 **포워딩을 막으면
  서비스 기능 자체(원격 데스크탑 프록시 등)까지 동작 불가**.
- **Windows 경로/줄바꿈/권한 의미 차이.** 점프호스트가 Windows이면 그 위에서
  rsync/ssh 래퍼를 돌릴 때 **POSIX 권한(1777/0644)·심볼릭 링크·`sudo`·소유자(stcx/
  koopark) 의미가 보존되지 않는다.** 본 시스템은 권한·UID/GID 동기화에 의존
  (예: VNC 디렉토리 1777, 노드 간 UID 일치)하므로, 경유 과정에서 메타데이터가
  유실되면 **배포는 됐는데 실행 권한이 깨지는** 문제가 생긴다.
- **2-hop scp/rsync의 취약성.** 게이트를 "복사→재복사"의 2단계로 우회하면(아래 2.1),
  각 hop마다 디스크 IO·임시 저장·정합성 검증이 중복되어 **증분성·원자성**이 사라진다.

### 1.5 규모(346대)에 따른 병목의 비선형 악화

배포 대상이 **346대**라는 점은 위 제약들을 산술이 아니라 **비선형으로** 키운다.

- **단일 게이트 통과 × 346.** 노드별 직접 전송이면 클러스터 내부 스위치 대역폭을
  346갈래로 나눠 쓰지만, 게이트 경유는 **모든 흐름이 게이트 1대의 NIC·세션 테이블·
  감사 로깅을 통과**한다. 게이트의 동시 세션·throughput 상한이 전체 동기화 시간을
  지배한다(1.2).
- **부분 실패의 확률 증가.** 346대 × (수 분~수십 분) 전송에서 게이트의 세션 TTL·
  재인증·큐 드롭이 한 번이라도 걸릴 확률이 노드 수에 비례해 커진다. 한 노드라도
  **부분 전송/체크섬 불일치**면 "전 노드 최신" 불변식이 깨진다(1.1).
- **재시도 폭증.** 실패 노드 재시도가 다시 게이트를 통과 → 피크 시간대 게이트 부하가
  눈덩이처럼 커져, 3일~1주일 주기의 **동기화 윈도우 초과**가 상시화된다.

직접·병렬 모델에서 27대로 빠듯하던 윈도우가, 346대 + 게이트 직렬화에서는 **현실적으로
주기 내 완료가 불가능한 규모**가 된다.

### 1.6 빌드 파이프라인(사내 리눅스 빌드 서버)의 게이트 종속

본 시스템은 단순 배포가 아니라 **빌드→동기화가 연결된 무인 파이프라인**이다.
apptainer 정의/소스에 변경이 생기면 **사내 리눅스 빌드 서버가 자동으로 `.sif`를
빌드**하고, 그 산출물을 클러스터로 **자동 동기화**한다. 빌드 서버와 클러스터(또는 그
관리 서버) 사이에 S-gate가 놓이면, **빌드 자동화의 산출물 전달 단계가 통째로 게이트에
묶인다.**

- **"변경 트리거 → 빌드 → 즉시 동기화"의 무인 연쇄가 끊긴다.** 빌드는 리눅스에서
  자동으로 끝나도, 그 결과를 게이트 너머로 보내는 마지막 hop이 **대화형 인증·세션
  승인**을 요구하면(1.3) 파이프라인이 사람의 개입 지점에서 정지한다. 빌드가 잦을수록
  (3일~1주일, 또는 변경 즉시) 이 수동 개입 빈도가 운영 부담으로 누적된다.
- **2단(빌드서버→게이트→클러스터) 경유.** 빌드 산출물은 (a) 빌드 서버에서 관리
  서버/미러로 1차 전달, (b) 거기서 346대로 2차 배포의 **2단계**를 거치는데, 게이트가
  1차 단계에 끼면 1.1~1.4의 모든 제약(터널 차단·증분 무력화·세션 직렬화·메타데이터
  비보존)이 **빌드 산출물 전달에 그대로 재현**된다.
- **빌드-배포 원자성 상실.** 이상적으로는 "빌드된 버전 N이 전 노드에 일괄 반영"되어야
  버전 정합성이 보장된다. 게이트가 중간에서 일부만 통과시키면 **노드 간 버전 혼재**
  (일부 N, 일부 N-1)가 발생해, 동일 잡이 노드에 따라 다른 전·후처리 바이너리로 도는
  **재현성·정합성 사고**로 이어진다.
- **CI/CD 관점의 단절.** 빌드 서버의 자동 빌드는 사실상 CI다. CI 산출물을 무인으로
  배포처에 push하지 못하면 **CD가 성립하지 않으며**, 게이트는 그 CD 경로의 단절점이 된다.

### 1.7 종합

본 시스템의 자동화 가치는 **"사내 빌드 서버가 변경을 자동 빌드 →
관리 서버가 346대 전 노드에 직접·병렬·무인·증분 rsync로 즉시 동기화"** 하는
**빌드-배포 무인 연쇄**에 있다. S-gate는 그 연쇄의 (직접·병렬·무인·증분) 네 전제와
**빌드→배포 자동 전달 단계**를 동시에 약화시킨다. 따라서 점프호스트 경유는
**단순히 느려지는 문제가 아니라, 빌드 자동화와 일괄 배포 모델 자체가 성립하지 않는**
구조적 제약이다.

## 2. 대체 방안 검토

| # | 대체 방안 | 개요 |
|---|----------|------|
| A | **OpenSSH ProxyJump(-J)/ProxyCommand 터널링** | S-gate를 SSH 다중-hop으로 투명 경유, rsync를 그 위로 |
| B | **게이트 내부에 중계 미러(스테이징) 서버** | 게이트 안쪽에 1대 미러를 두고, 외부→미러 1회, 미러→전노드 병렬 |
| C | **풀(pull) 모델 + 콘텐츠 미러** | 각 노드가 정해진 시각에 내부 미러에서 스스로 rsync/apt pull |
| D | **오프라인 매체(스니커넷) 정기 반입** | sif/패키지를 물리 매체로 게이트 안쪽에 주기 반입 |
| E | **델타/블록 동기화 도구 전환** | rsync 대신 zsync·casync·bittorrent 등으로 게이트 부하 완화 |
| F | **컨테이너 레지스트리(OCI) 기반 배포** | sif 대신 OCI 이미지를 내부 레지스트리에 push, 노드가 pull |

각 방안의 적용 어려운 사유는 3장에서 일대일로 서술한다.

## 3. 대체 방안별 적용이 어려운 사유

### 3.1 A안 — ProxyJump/ProxyCommand 터널링

- S-gate가 **SSH 포트포워딩·`-J`·`-W`를 정책적으로 차단**하면 ProxyJump 자체가
  성립하지 않는다(1.4). 보안 게이트의 존재 이유가 "임의 터널 차단"이므로, 이를
  허용받는 것은 **보안정책 예외 승인** 문제로 귀결된다.
- 허용되더라도 **대화형 인증(OTP/SSO)** 이 끼면 무인 ProxyJump가 불가(1.3).
- 게이트가 **SSH 프록시(프로토콜 종단·재개시)** 형태면 raw 채널이 깨져 rsync
  델타가 무력화(1.1).

### 3.2 B안 — 게이트 안쪽 중계 미러(스테이징)

- 가장 현실적이나, **게이트 안쪽에 상시 가동 서버 1대를 신규 배치·운영**해야 한다.
  → 자산 도입·전력·관제·보안 인증(망분리 환경의 신규 호스트 등록)에 대한
  **별도 승인·검증 절차**가 필요하고, 폐쇄망에서는 이 자체가 수개월짜리 행정 과제다.
- 외부→미러 1회 전송도 결국 **게이트를 통과**하므로, 게이트가 대화형/직렬화면
  3일~1주일 주기의 235 GB급 반입 윈도우를 보장 못 함(1.2).
- 미러→전노드는 내부망이라 빠르지만, **미러의 최신성**을 보장하려면 외부 동기화가
  자동·무인이어야 하는데 그 지점이 다시 게이트 제약에 묶임(1.3).

### 3.3 C안 — 풀(pull) 모델 + 내부 콘텐츠 미러

- 각 노드가 스스로 당기려면 **내부 미러(apt repo/파일서버)가 항상 최신**이어야 하고,
  그 미러를 외부에서 갱신하는 경로가 다시 게이트를 통과(3.2와 동일한 병목).
- 노드 측 cron pull은 **노드의 외부 도달성**을 요구하는데, 폐쇄망 정책상 compute
  노드가 게이트 너머를 직접 보는 것은 보통 금지된다. → 결국 "미러까지만 push,
  노드는 미러에서 pull"로 귀착되어 **B안의 제약을 그대로 상속**.

### 3.4 D안 — 오프라인 매체(스니커넷) 정기 반입

- 3일~1주일 주기로 **8.7 GB×갱신분을 사람이 물리 반입**해야 한다. 본 시스템의
  목표인 "항상 최신 자동 동기화"와 **무인 자동화 원칙에 정면으로 배치**(1.3).
- 매체 반입은 **보안 검역(악성코드 검사·반입 승인·매체 등록)** 절차를 매 회 거쳐야
  하므로, 짧은 주기에는 **행정 비용이 전송 비용을 압도**한다.
- 증분성이 없어 매 회 전량/수동 관리 → 정합성·이력 추적이 취약.

### 3.5 E안 — 델타/블록 동기화 도구 전환(zsync/casync/torrent)

- 게이트 통과 데이터량은 줄일 수 있으나, **게이트가 raw TCP/포워딩을 막는 한**(1.1,
  1.4) 어떤 전송 도구든 **채널 자체를 못 여는** 문제는 동일하다. 도구를 바꿔도
  "경유 가능성"이 해결되지 않으면 무의미.
- 폐쇄망·보안망에서 **신규 프로토콜/포트(torrent 등) 허용**은 보안정책상 거의 불가.
- 노드 측에 신규 클라이언트(casync 등)를 까는 것도 본 시스템의 **오프라인 패키지
  검증 체계**에 추가 항목으로 들어가야 함(유지보수 부담 증가).

### 3.6 F안 — 컨테이너 레지스트리(OCI) 기반 배포

- 본 시스템은 **단일 파일 `.sif`(SIF)** 를 직접 rsync하는 모델이다. 레지스트리
  전환은 **빌드 파이프라인·노드 pull 체계·레지스트리 서버**를 새로 세워야 하고,
  그 레지스트리 역시 외부 갱신 시 **게이트를 통과**(3.2 병목 상속).
- 레지스트리 pull도 **노드의 레지스트리 도달성**을 요구 → 폐쇄망에서 내부 레지스트리로
  귀착, 그 최신화는 다시 게이트 의존.
- OCI 레이어 캐시 이점은 있으나, 전·후처리 프로그램이 통째 든 대형 단일 이미지를
  3일 주기로 통째 갱신하는 패턴에서는 **레이어 재사용 이득이 작다**.

## 4. 결론

본 시스템의 배포·동기화 자동화는 **"사내 리눅스 빌드 서버의 자동 빌드 → 관리 서버가
346대 전 노드에 직접·병렬·무인·증분 rsync로 즉시 동기화"** 라는 **빌드-배포 무인
연쇄** 위에 서 있다(코드 근거: `sync_apptainers_to_nodes.sh`,
`phase10_compute_deploy.sh`). 이 연쇄는 네 전제 — **직접·병렬·무인·증분** — 와
**빌드→배포 자동 전달**에 의존한다.

Windows 점프호스트(S-gate)는 그 설계상 **임의 터널·포워딩 차단, 대화형 인증 강제,
세션 직렬화·감사·동시연결 제한, POSIX 메타데이터 비보존**을 본질로 하므로, 위 네
전제와 빌드 산출물 전달 단계를 동시에 약화시킨다. 특히 **346대 규모**에서는 게이트
단일 통과 병목과 부분 실패 확률이 비선형으로 커져, 3일~1주일 동기화 윈도우 내
완료가 사실상 불가능해진다(1.5). 또한 빌드 서버가 게이트 너머에 있으면 **CI(자동 빌드)는
되어도 CD(무인 일괄 배포)가 단절**된다(1.6).

검토한 대체 방안(A~F)은 모두 **"게이트를 통과하는 자동·무인·증분 경로"** 라는 근본
난점으로 수렴하며, 각 방안은 (a) 보안정책 예외 승인(터널·신규 포트 허용), (b) 폐쇄망
신규 자산 도입 절차(미러·레지스트리 호스트 등록·검증), (c) 무인 자동화와 대화형
게이트의 원리적 충돌 중 하나 이상에 걸려 **3일~1주일 주기의 346대 최신 동기화라는
운영 목표를 충족하지 못한다.**

따라서 점프호스트(S-gate) 경유 구조에서는, 본 시스템이 제공하는 **빌드 자동화와
고빈도·대용량·무인 일괄 동기화의 핵심 가치를 그대로 살리기 어렵고**, 이를 우회하려면
**게이트 안쪽 중계 미러(B안)에 대한 보안·행정 승인**과 **빌드 서버↔미러 간 무인 전달
경로 확보**를 동시에 전제로 한 부분적 절충만이 현실적 후보로 남는다. 그러나 그 절충마저
빌드 산출물의 1차 반입이 게이트를 통과해야 하는 한, 빌드-배포 무인 연쇄의 **완전한
자동화는 달성되지 않는다.**
