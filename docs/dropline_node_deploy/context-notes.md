# 컨텍스트 노트 — 노드 SIF 배포 안전

## 2026-11-14 착수

- 요청 원문은 hwaxportal-a5 → -35 경유로 받았다(11-12). 2·3번은 -35, 1번은 이 세션(사용자 승인).
- **같음 판정을 "크기+mtime 일치"로 한 이유.** 기존 규칙 `로컬 mtime ≤ 원격 mtime이면 같다`는 같은 크기의 더 오래된 빌드로
  되돌릴 때(롤백) 건너뛴다. 포털이 짚은 "크기가 같은 다른 빌드"가 바로 이 경우다. 일치 규칙이 성립하려면 설치할 때 원격
  mtime을 원본 값으로 맞춰야 해서 `touch -m -d @<epoch>`를 넣는다.
  대가 — 지금 노드 사본의 mtime은 복사 시각이라 바뀐 판정으로 처음 돌리면 해당 이미지가 한 번 다시 복사된다.
  `--sha256`으로 돌리면 내용이 같을 때 복사 없이 mtime만 맞추므로 첫 실행은 `--sha256` 권장.
- **phase8 일반 경로의 판정은 유지.** 바꾸면 전 이미지가 356대에 한 번씩 다시 복사된다. 설치 때 mtime을 맞추므로 기존
  규칙(`≤`)으로도 이후 판정은 정상이다. 롤백까지 정확히 하려면 `--image`를 쓴다.
- **원자 교체 방식.** 대상 디렉토리 안의 `dst.part`를 거쳐 `mv -f`(rename(2))로 바꾼다. rename은 새 inode로 바꾸므로
  기존 SIF를 열거나 마운트한 프로세스는 옛 inode를 계속 본다. `cp`로 기존 파일에 덮어쓰면 같은 inode를 잘라 쓰므로 깨진다.
  스테이징이 대상과 같은 장치면 `mv`(복사 0번), 다르면 `cp`로 `.part`를 만든다(같은 FS 안으로 한 번).
- **원격 실행은 `declare -f`로 함수를 보내는 방식.** SSH_BASE에 `-n`이 있어 stdin으로 스크립트를 보낼 수 없고,
  로컬(컨트롤러)과 원격에서 같은 구현을 쓰기 위해서다.
- **"컨트롤러 사본도 같은 차례로"의 해석.** phase8은 컨트롤러에 SIF를 두지 않는다(헤드노드에는 메타데이터 JSON만).
  컨트롤러 SIF 사본이 있는 곳은 deploy_apptainers.sh뿐이라 거기에 같은 절차를 적용한다. -35 해석(같은 FS 스테이징·원자
  교체·검증을 똑같이)과 같다.
- **deploy_compute_images.sh.** `.gitignore:78`이 `apptainer/` 전체를 제외해 이 파일은 git에 없다. 각 호스트에 따로 놓인
  로컬 파일이라 git으로는 지울 수 없고, git에 스텁을 넣으면 그 파일이 있는 호스트에서 pull이 충돌한다. 그래서 git에 있는
  유일한 호출처인 phase3 Step 16만 막는다.
- **조사 중 발견한 결함.**
  - phase8 L645 `scp -C $SCP_OPTS` — phase8 안에서 SCP_OPTS가 정의되지 않음(ssh_helpers.sh의 setup_node_ssh_opts 안에서만

    `((fail++))`로 넘어가고 그것도 1이라 스크립트가 끝난다. 마지막 줄은 실패가 있어도 `exit 0`.

  최대 8 GiB. 로컬 시험으로 대신하고, 실노드는 포털 VM 켜기 + 사용자 승인 뒤에.

## 2026-11-14 구현 중 추가 결정

- **스테이징 후보 순서를 /scratch, $HOME, /tmp 로.** 같은 장치인 후보가 있으면 순서와 상관없이 그걸 고르므로 원자성에는 영향이 없다.
  같은 장치 후보가 없을 때의 대체 후보만 달라진다 — 운영 /home 이 NFS 면 홈은 작거나 공유일 수 있어 로컬 디스크(/scratch)를 먼저 쓴다.
  기존 phase8 도 /scratch 를 먼저 썼다. node001(dev)은 $HOME 과 /opt 가 같은 vda2 라 어느 순서든 $HOME 이 잡힌다.
- **스테이징 파일 이름에 대상 노드 이름을 넣는다** (`.<img>.<host>.incoming`). 스테이징이 노드 간 공유 FS(NFS 홈 등)면 병렬 배포에서
  여러 노드가 같은 경로에 동시에 써 파일이 섞일 수 있다. 기존 deploy_apptainers.sh 의 `~/<img>` 도 같은 위험이 있었다.
- **교체에는 대상 FS 여유가 이미지 하나만큼 더 필요하다.** rename 직전까지 옛 사본과 새 사본이 함께 있다. 그래서 복사 전에
  `sif_pick_staging` 이 대상 FS(와 다른 FS 스테이징이면 그쪽도) 여유를 확인하고 모자라면 복사하지 않고 실패한다.
- **sha256 불일치로 중단하면 스테이징 사본도 사라진다**(같은 FS 면 .part 로 옮긴 뒤 지움). 깨진 사본이라 다시 받는 게 맞다.
- **--image 에서 --dry-run 은 --verify-only 와 같게** 처리했다. 예전에는 --image 가 --dry-run 을 무시하고 실제로 배포했다.
- **phase8 --image 가 이제 --nodes-file 을 따른다.** 예전에는 무시하고 YAML 전 노드에 배포했다.
- **시험 방법.** phase8 끝의 `main "$@"` 를 직접 실행할 때만 돌게 바꿔(source 가드) 함수만 불러 시험한다. sudo 는 chown 만 건너뛰는
  대용 함수, ssh/scp 는 로컬 실행 가짜. 열어 둔 fd 시험은 옛 방식(cp 덮어쓰기)이면 새 내용이 보여 실패함을 따로 확인했다.
